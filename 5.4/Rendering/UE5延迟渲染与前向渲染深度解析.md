# UE5 延迟渲染与前向渲染深度解析

> 目标读者：已经具备基本图形学常识（知道顶点/像素着色器、知道光照计算是怎么回事），想真正搞清楚 UE5 两种渲染路径的原理、区别、关系与工程取舍的人。
>
> 读完后你应该能回答：为什么 UE5 默认用延迟渲染？为什么半透明物体仍然走前向路径？为什么 VR 模板推荐前向渲染？Lumen 和 Nanite 跟这两种路径是什么关系？

---

## 一、先建立共同的认知框架：一个像素是怎么被"照亮"的

无论哪种渲染路径，最终目的都一样：对屏幕上每个像素，算出它最终的颜色。这个颜色通常可以抽象成：

```
最终颜色 = 材质属性(反照率、粗糙度、金属度、法线...) 参与 光照计算(所有光源的贡献累加)
```

关键矛盾在于：**几何体的光栅化**和**光照计算**这两件事，谁先谁后、如何对应。

- 几何体光栅化：把三角形投影到屏幕，确定"这个像素画的是哪个物体的哪个表面点"。
- 光照计算：对表面点执行着色模型（如 PBR），把场景里所有光源对它的贡献加起来。

传统做法是让这两件事"同时发生"——每画一个物体，就在它的像素着色器里算光照。这就是**前向渲染（Forward Rendering）**。

延迟渲染（Deferred Rendering）则反过来：**先光栅化、不点灯，把材质属性存下来；之后再统一对每个像素做光照**。

这个"先后次序"的差异，是理解后面一切区别与取舍的根源。

## 二、前向渲染（Forward Rendering）原理

### 2.1 基本流程

前向渲染是图形管线最"朴素直观"的形态：

```
对场景中的每个物体（经过剔除后）：
    顶点着色器：变换顶点、输出插值数据
    光栅化：确定覆盖哪些像素
    像素着色器：拿到材质属性 + 读取"哪些光源影响这个物体"
                → 循环累加所有光源的 BRDF 贡献 → 输出最终颜色
```

每个物体画完，它覆盖的像素就有了最终颜色（写入颜色缓冲），同时写入深度缓冲（Z-Buffer）做遮挡剔除。

### 2.2 光照的两种处理方式

前向渲染内部又有两种实现变体：

**（a）经典前向（Classic Forward）**
着色器在编译时就写死"最多支持 N 个光源"。画每个物体时，把当前影响它的光源参数作为 uniform 传入，像素着色器循环累加。缺点是支持的灯数上限低，想加灯就得重新编译着色器变体，而且**所有像素都算所有灯**，哪怕那盏灯实际只影响一小块区域。

**（b）集群前向（Clustered Forward，UE4.26+ 的移动前向渲染器就是这种思路）**
事先把屏幕切成分块（tile），深度方向再切片，形成三维的"集群（cluster）"网格。预处理阶段把每盏灯塞进它影响的 cluster 里。画物体时，像素着色器根据自己所在 cluster 只遍历相关的灯。这样灯数上限大幅提高，但**逐像素仍然是在画物体的同时算光照**——这一点没有变，所以它仍然是前向渲染。

### 2.3 前向渲染的本质特征

- **几何处理次数 = 光照计算次数**：同一像素被多少个物体（三角形）覆盖，就要算多少次光照（虽然有深度测试会拒绝一部分，但 overdraw 部分仍然浪费）。
- **光照和材质耦合在同一个 shader 里**：想加一种新的着色模型，改的是同一个大 shader。
- **颜色缓冲直接产出最终颜色**：没有中间数据，不需要额外的内存存放材质属性。

## 三、延迟渲染（Deferred Rendering）原理

### 3.1 核心思想：把"画几何"和"算光照"彻底拆开

延迟渲染把渲染拆成两个大阶段（pass）：

**阶段一：几何 Pass（Base Pass / G-Buffer Pass）**

画所有不透明物体，但**不算任何光照**。像素着色器只负责把"光照计算需要的原材料"写入一组称为 **G-Buffer（几何缓冲）** 的多张渲染目标（MRT，Multiple Render Targets）：

| G-Buffer 通道（UE5 典型布局，简化） | 存放内容 |
|---|---|
| GBufferA | 世界空间法线 + 逐像素 AO |
| GBufferB | 金属度、高光度、粗糙度 + Shading Model ID |
| GBufferC | 基础色（Base Color）+ 自定义数据 |
| GBufferD/E/F | 自定义数据、预计算阴影因子等 |
| Depth / Stencil | 深度与模板 |

**阶段二：光照 Pass（Lighting Pass）**

几何 Pass 结束后，屏幕上的每个像素都已经有了完整的"材质描述"。此时不再画任何物体，而是**逐光源、逐像素**做光照：

- 经典做法：对每盏灯画一个覆盖其影响范围的几何体（点光画球、聚光画锥、平行光全屏），在像素着色器里从 G-Buffer 读出材质属性，算这盏灯的 BRDF 贡献，**累加**进光照缓冲。
- UE4/UE5 的做法：**集群延迟着色（Clustered Deferred Shading）**。和集群前向一样把屏幕分块、每块只处理相关灯，但光照计算发生在独立的计算着色器里，从 G-Buffer 取数据——所以它仍是延迟渲染。

### 3.2 为什么"延迟"能解决灯多的问题

看一个复杂度对比。设场景有 G 个像素被物体覆盖（考虑 overdraw 后是 G' ≥ G），L 盏灯：

- **前向**：光照计算次数 ≈ G' × L。每个被覆盖的像素（哪怕最后被遮挡丢弃），在画它的那一刻都算了一遍所有灯。灯越多、overdraw 越严重，浪费越大，而且是乘法增长。
- **延迟**：光照计算次数 ≈ 屏幕可见像素数 × L。几何 Pass 结束后，深度测试已经筛掉了被遮挡的像素，**每个屏幕像素只算一次光照**，不管它被多少物体覆盖过。光照复杂度与场景几何复杂度**解耦**了。

这就是"延迟"二字的含义：**把光照推迟到可见性确定之后**。

### 3.3 延迟渲染的本质特征

- **光照与几何解耦**：加 100 盏灯，几何 Pass 成本不变；加 100 个物体，光照 Pass 成本不变。两者可以独立分析和优化。
- **材质属性以"数据"形式存在**：光照 Pass 看到的是统一的 G-Buffer，光照代码只需写一份，与材质系统解耦。
- **屏幕空间后处理天然受益**：SSAO、SSR、屏幕空间阴影等效果需要的深度、法线、粗糙度都在 G-Buffer 里，直接可用。UE 里大量后处理效果就是建立在 G-Buffer 之上的。
- **代价是带宽和内存**：G-Buffer 是一组全分辨率的大纹理，写一次、读多次。4K 分辨率下这是数 GB/s 级别的带宽压力。这也是移动端不轻易用完整延迟渲染的原因之一。

## 四、两者的正面对比

| 维度 | 前向渲染 | 延迟渲染 |
|---|---|---|
| **光照成本模型** | 像素覆盖数 × 灯数，overdraw 放大浪费 | 可见像素数 × 灯数，与几何解耦 |
| **大量动态灯** | 差（每像素循环所有灯） | 好（这正是它存在的理由） |
| **G-Buffer 内存/带宽** | 无 | 大，是高分辨率下的主要瓶颈 |
| **MSAA（多重采样抗锯齿）** | 天然支持 | 与 MRT 结合代价高，基本放弃（UE 用 TAA/TSR 替代） |
| **透明物体** | 天然支持（按由远到近排序混合即可） | **不支持**，因为透明物体不写深度、一个像素叠多层材质，G-Buffer 单像素只能存一份材质 |
| **材质多样性** | 每个物体可以用完全不同的着色模型和 shader | G-Buffer 布局固定，所有材质必须挤进同一套属性格式；特殊着色模型（如皮肤、毛发、清漆）要靠 Shading Model ID 在光照 pass 里分支处理 |
| **前向-only 特性** | 支持逐像素特殊混合、自定义深度混合等 | 部分材质表达式/混合模式在延迟路径下不可用或受限 |
| **屏幕空间效果（SSAO/SSR 等）** | 需要额外的 Pre-Pass 生成深度法线 | G-Buffer 现成，几乎免费接入 |
| **着色器复杂度管理** | 光照 × 材质 × 阴影的各种排列组合爆炸成大量 shader 变体 | 光照 shader 一份，材质 shader 只管输出 G-Buffer |

一句话总结这张表：

> **延迟渲染用"内存带宽 + 透明/MSAA 的不便"换来了"光照与几何解耦 + 统一的屏幕空间数据"；前向渲染用"光照效率的上限"换来了"简单、省带宽、透明和 MSAA 自由"。**

## 五、UE5 中的真实图景：不是二选一，而是配合使用

理解 UE5 的关键一步：**UE5 的默认渲染器叫"延迟渲染器"，但它内部一直包含一条前向路径**。两者在每一帧里是协作关系。

### 5.1 每帧的真实分工（桌面端默认延迟渲染器）

1. **Depth Pre-Pass（可选）**：先画一遍深度，减少 Base Pass 的 overdraw。
2. **Base Pass（延迟路径主体）**：不透明物体写 G-Buffer。UE5 中开启 Nanite 后，虚拟化几何体走 Nanite 管线，但最终仍然输出到同一套 G-Buffer——**Nanite 解决的是"几何怎么高效光栅化"，不改变"延迟还是前向"这个光照架构问题**。
3. **光照阶段（延迟路径）**：
   - 直接光：集群延迟着色 + 阴影贴图/虚拟阴影贴图（VSM）。
   - 间接光：**Lumen**（软件/硬件光线追踪或 Surface Cache）计算全局光照与反射，其结果再与 G-Buffer 合成。Lumen 依赖 G-Buffer 提供的场景表面描述，可以说它"长在"延迟架构上。
4. **半透明 Pass（前向路径）**：所有半透明材质、体积雾/云等，在光照完成后**按从远到近排序，用前向方式画进同一张颜色缓冲**。它们需要的灯照，由集群前向逻辑（和前面讲的 clustered forward 同构）现场计算；半透明物体也能接收来自 Lumen 的间接光近似。
5. **后处理链**：TAA/TSR、Bloom、色调映射等。

所以"UE5 用延迟渲染"这句话的准确版本是：**UE5 的不透明物体光照走延迟路径，半透明物体走前向路径，两条路径在同一帧内前后衔接、共用同一个颜色缓冲。**

### 5.2 为什么半透明必须走前向

回到 G-Buffer 的根本限制：一个像素只能存一份材质属性。透明玻璃后面还有墙，墙后面可能还有东西——延迟路径无法表达"这一像素有多层"。而前向渲染天生支持 alpha 混合：先画好的背景就在颜色缓冲里，透明物体直接混合上去。这是两条路径配合的最典型例子。

### 5.3 UE 提供的"整体切到前向"选项

UE 还保留了一个完整的前向渲染器（项目设置 → Rendering → Forward Shading），主要面向两类场景：

- **VR**：VR 需要高帧率、低延迟，且 MSAA 对 VR 的头显畸变和边缘闪烁特别重要——前向 + MSAA 的组合在这时比延迟 + TAA 更合适。UE 官方 VR 模板即推荐前向渲染。开启后，不透明物体也走前向（带集群光照），并支持多重采样抗锯齿。
- **移动端**：移动 GPU 的带宽极其宝贵，完整 G-Buffer 写读开销吃不消，所以移动端用前向（或 UE 后续引入的移动端延迟，做了大量裁剪）。

### 5.4 配合使用的高级例子

- **Forward Shading + D-Buffer 贴花**：即使在前向渲染器里，UE 仍可以画一层 Decal Buffer 来支持贴花——局部借用"先存数据再合成"的延迟思想。
- **延迟渲染器中的逐对象前向特性**：某些材质特性（如次表面散射的一部分、薄透明 shading model）在延迟路径下走特殊分支，本质上是在延迟框架里开小灶的前向式处理。
- **Lumen + 前向半透明**：半透明物体不写入 Lumen 的场景描述，但采样 Lumen 的结果来照亮自己——延迟路径产出的数据反哺前向路径。

## 六、使用例子与选型决策

### 例 1：大型开放世界游戏（默认延迟渲染器）

场景：城镇夜景，数百盏动态路灯、霓虹灯、车灯；大量 SSAO/SSR/Lumen 效果。

- **选择**：延迟渲染器（UE5 默认）。
- **理由**：灯多 → 前向的"像素 × 灯数"成本爆炸，延迟的解耦优势压倒一切；屏幕空间效果要 G-Buffer；玻璃、雨幕等透明效果由前向半透明 pass 兜底。
- **代价管理**：4K 下注意 G-Buffer 带宽，可用 GBuffer 压缩格式、控制 Base Color 精度。

### 例 2：VR 游戏

场景：90Hz 起步，眩晕零容忍，画面里灯不算多。

- **选择**：Forward Shading + MSAA。
- **理由**：MSAA 对 VR 画质收益大且前向天然支持；没有 G-Buffer 的固定开销，帧时间更可控；TAA 在 VR 中的重影问题被规避。
- **代价管理**：灯数需要收敛（烘焙 + 限制动态灯）；部分依赖 G-Buffer 的后处理效果不可用或需替代方案。

### 例 3：手游（中高画质）

场景：PUBG 类，大地图、适量动态光。

- **选择**：移动前向渲染器（或评估 UE5 移动延迟，视目标机型带宽而定）。
- **理由**：带宽即电量、即发热；前向的零 G-Buffer 开销是决定性的。
- **代价管理**：尽量烘焙光照，动态灯屈指可数。

### 例 4：混合现实的过场演出

场景：大量玻璃材质的高精度产品展示（汽车配置器）。

- **选择**：默认延迟渲染器，玻璃等全部走半透明前向 pass，配合 Lumen 反射与高质量透明光照。
- **要点**：这正是"延迟 + 前向配合"的日常形态——你什么都不用切，UE 每帧都在这么做。你需要关心的是透明物体的排序、refraction 设置和半透明光照精度。

## 七、收束：一张脑图

```
渲染的根本问题：对每个像素，结合材质与光照算颜色
│
├── 前向渲染：画物体的"同时"算光照
│     ├── 优点：省带宽、支持 MSAA、支持透明、材质自由
│     ├── 缺点：光照成本 = 覆盖像素 × 灯数，灯多即死
│     └── UE5 中的位置：VR/移动端整体方案；桌面端每帧的半透明 pass
│
├── 延迟渲染：先存材质（G-Buffer），再统一算光照
│     ├── 优点：光照与几何解耦、屏幕空间效果免费、灯多不怕
│     ├── 缺点：G-Buffer 带宽/内存、不支持 MSAA 与透明、材质格式受限
│     └── UE5 中的位置：桌面/主机默认；Nanite 喂给它几何，Lumen 长在它上面
│
└── 关系：不是对立，是同一帧里的分工
      不透明 → 延迟路径（产出 G-Buffer + 光照 + Lumen 数据）
      半透明 → 前向路径（消费颜色缓冲，复用 Lumen 结果）
      VR/移动 → 整条管线切到前向（+MSAA）
```

掌握到这一层，你看 UE5 渲染器的任何一项设置——Forward Shading 开关、Nanite、Lumen、半透明材质选项、MSAA/TAA 之争——都能立刻知道它在两条路径的版图里处于什么位置、动了哪块成本。
